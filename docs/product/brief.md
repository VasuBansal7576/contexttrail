# ContextTrail product brief

Updated 4 October 2026 from the owner's explicit product requirements. This brief owns product scope. The older image-first specification is a historical technical record; its scope freeze does not limit this product.

ContextTrail investigates a question, claim or piece of media. It finds sources automatically, compares what they say, distinguishes event dates from publication and retrieval dates, explains supported and conflicting evidence, and preserves the investigation for later inspection and correction.

## Required experience

One clear starting point accepts a question, claim, image or video. Retrieval is the main workflow. Manual evidence entry is an optional correction and investigation tool. Results lead with an evidence-bound explanation, then let the reader inspect retained passages, source relationships and chronology inside the app. Opening an original source is deliberate. Unknowns remain visible. Saved investigations retain their input question, evidence, assessments and correction history.

The frontend follows the owner's authored editorial HTML direction: Instrument Serif, Geist Sans, warm paper, brick red and blue chapter contrasts, composed illustration and gradual meaningful reveals. ## Required scope and acceptance

| Workflow | Required outcome | Baseline on d881a58 |
| --- | --- | --- |
| Open question, including UPI in India | Automatically find and read sources, compare explanations, offer an evidence-linked research account | Retrieves eight leads and source assessments; no integrated explanation |
| Specific news or product claim | Show scoped support, challenge, context and unknowns with inspected passages | Source report exists; live coverage acceptance open |
| Image with changed caption | Find earlier appearances and context shifts; distinguish exact identity from visual leads | Image executor exists; strong real case acceptance open |
| Video trail | Investigate timestamped segments despite cropping, shortening and captions | Searches one representative frame; local supplied-media comparison exists |
| Claim family | Connect variants across time with proven, plausible and unresolved relationship labels | Supplied family links through CLI only |
| Brand/product investigation | Search impartially, inspect dependencies, retain conflicting evidence | General question workflow can accept input; specialised experience absent |
| Watchlist | Run fresh checks, retain genuinely new evidence and variants, show changes and failures without treating missing results as deletion | Supplied snapshot comparison only; automatic monitoring absent |
| Reviews, work attribution and shopping mismatch | Investigate patterns, independence, earlier appearance and supplied-media differences without automatic accusations | Partial generic/local tools; specialised acceptance absent |
| Audio | Include in broader media research, with actual decoding/transcription before making audio claims | No automatic audio research |

Government targeting is outside scope. Earliest found appearance never proves authorship. Multiple sources never prove independence merely because their domains differ. A model classification never supplies missing evidence.

The baseline column above records `d881a58`, not the latest implementation. The current branch adds expanded question retrieval and source facets, one-hop citation recovery, full-track local luminance scanning and speech recognition, separate spoken-source research, cross-saved-source wording groups, automatic watches and two-still local comparison. The current specification and work log distinguish tested software paths from real product acceptance. These additions do not shrink the required outcomes above.

## Completion rule

A workflow is accepted only after a real product UI run exercises its intended outcome. Unit tests and controlled results prove software behavior separately. Each release records source revision, input, provider usage, retained output, inspected sources, screenshots and save/reopen behavior. Bugs belong on GitHub with reproduction and verification. Existing acceptance gaps stay in their original issues.

The launch video and interactive explanation must use actual accepted outputs and real interface captures. They must describe why someone would use the product and show the search-to-evidence flow. Fictional sources, scripted mock results and planned tools cannot appear as working functionality.
